## Problem Statement

The Responses API structured output (`text.format.json_schema` with `strict: true`) requires **every object** in the JSON schema to have `additionalProperties: false`. The current `_patch_schema_for_strict()` in `responses_api_llm.py` handles:
- ✅ Top-level objects
- ✅ Nested `properties`
- ✅ Array `items`
- ✅ `$defs` entries

But it **misses**:
- ❌ `anyOf` sub-schemas (generated by `Optional[X]` fields in Pydantic v2)
- ❌ `oneOf` sub-schemas
- ❌ `allOf` sub-schemas (less common but possible)
- ❌ `$ref` resolution (Pydantic v2 may generate `$ref` pointing to `$defs`)

Without this fix, **any Pydantic model with Optional fields** will fail with HTTP 400 when used with `ResponsesAPILLM.structured_predict()`.

## Implementation Plan

### Phase 1: Fix `_patch_schema_for_strict()` (the core fix)

**File:** `worker_plan/worker_plan_internal/llm_util/responses_api_llm.py`

**What to change:** Extend `_patch_schema_for_strict()` to recurse into `anyOf`, `oneOf`, and `allOf` arrays.

**Exact fix:**

```python
def _patch_schema_for_strict(schema: dict) -> dict:
    """
    Recursively ensure every object in the schema has additionalProperties: false.
    Required for strict mode in the Responses API.
    
    Handles:
    - Direct object schemas
    - Nested properties
    - Array items
    - $defs entries
    - anyOf/oneOf/allOf sub-schemas (from Optional fields, unions, etc.)
    """
    schema = dict(schema)
    if schema.get("type") == "object":
        schema.setdefault("additionalProperties", False)
        if "properties" in schema:
            schema["properties"] = {
                k: _patch_schema_for_strict(v)
                for k, v in schema["properties"].items()
            }
    if "items" in schema:
        schema["items"] = _patch_schema_for_strict(schema["items"])
    if "$defs" in schema:
        schema["$defs"] = {
            k: _patch_schema_for_strict(v)
            for k, v in schema["$defs"].items()
        }
    # Handle anyOf/oneOf/allOf — generated by Optional[X], Union types, etc.
    for combiner in ("anyOf", "oneOf", "allOf"):
        if combiner in schema:
            schema[combiner] = [
                _patch_schema_for_strict(sub) for sub in schema[combiner]
            ]
    return schema
```

**Why this works:** Pydantic v2 generates `Optional[str]` as:
```json
{"anyOf": [{"type": "string"}, {"type": "null"}]}
```
The string/null sub-schemas don't have `type: "object"` so `additionalProperties` won't be added to them (correct behavior). But `Optional[SomeModel]` generates:
```json
{"anyOf": [{"$ref": "#/$defs/SomeModel"}, {"type": "null"}]}
```
The `$ref` resolves to a `$defs` entry which IS an object — already handled. And direct inline object definitions in `anyOf` will get patched too.

### Phase 2: Add `required` field enforcement

The Responses API strict mode also requires that **all properties must be listed in the `required` array**. Optional fields in Pydantic don't include them in `required` by default. Add this to the patch function:

```python
    if schema.get("type") == "object" and "properties" in schema:
        # Strict mode requires ALL properties in required array
        schema["required"] = sorted(schema.get("properties", {}).keys())
```

**Important:** This means the LLM must produce values for "optional" fields too (typically `null`). The Responses API enforces that the output includes every field — it just allows `null` for nullable types. This is by design in strict mode.

**File:** `worker_plan/worker_plan_internal/tests/test_schema_strict_mode.py`

Test cases:

### Phase 4: Defensive `input_text` coercion (from staging2 lesson)

**File:** `worker_plan/worker_plan_internal/llm_util/responses_api_llm.py`

In `_messages_to_input()`, ensure content items use `type: "input_text"` not `type: "text"`:

```python
def _messages_to_input(messages: Sequence[ChatMessage]) -> list:
    """Convert llama_index ChatMessage list to Responses API input array."""
    result = []
    for msg in messages:
        role = msg.role.value if hasattr(msg.role, "value") else str(msg.role)
        content = msg.content or ""
        # Responses API requires "input_text" for input items, not "text"
        # This is a known gotcha from the staging2 implementation
        if isinstance(content, list):
            coerced = []
            for item in content:
                if isinstance(item, dict) and item.get("type") == "text":
                    item = {**item, "type": "input_text"}
                coerced.append(item)
            content = coerced
        result.append({"role": role, "content": content})
    return result
```

**Note:** Current code passes content as plain strings, so this is future-proofing for when multi-modal content items are used. Low cost, high safety.

## Risk Assessment

- **Phase 1 (anyOf/oneOf/allOf):** Zero risk. Pure additive recursion. Can't break existing behavior.
- **Phase 2 (required enforcement):** Low risk. May surface if any model has computed/derived fields that shouldn't be in the schema. Audit needed.
- **Phase 3 (tests):** Zero risk.
- **Phase 4 (input_text coercion):** Zero risk. Only activates on list-type content, which isn't used yet.
